# D348 pinned R4b method

This overlay pins each benchmark side to two CPUs on the 6-vCPU perf VM. CPUs
1–2 belong to side A, CPUs 3–4 belong to side B, and CPUs 0 and 5 are reserved
for host services and housekeeping. The guest reports six vCPUs as six virtual
core IDs, but the maintainer's host mapping places each pair on one physical
core: vCPU 1 and 2 on host core 5, vCPU 3 and 4 on host core 6, and vCPU 0 and 5
on host core 7. Thus each measured side gets one whole physical core, and the
housekeeping pair gets the third. The host mapping is recorded with the guest
topology because it is not visible in the guest's `lscpu` output. This layout
applies to every engine, including kernel WireGuard and wireguard-go.
The harness, its audit sampler, and the `perf-run` launcher are also restricted
to CPUs 0 and 5, so they are not exempt from the runnable-task audit.

## Placement and restore

Inside the `perf-run` scope, the overlay reads each unit's `ControlGroup` and
captures `cpuset.cpus` and `cpuset.cpus.effective` from the matching cgroup.
It accepts the reboot baseline when `init.scope`, `system.slice`, and
`user.slice` either have configured `cpuset.cpus=0-5` or an empty configured
mask that inherits effective `0-5`. It captures those exact configured and
effective values, then pins the slices to 0–5's housekeeping subset, CPUs 0
and 5. Active host services inherit the system slice mask;
NetBird, Tailscale, containerd, Docker, and journald are checked from their
live cgroup masks. The configured `perf.slice` baseline is 1–3 and expands to
0–5 for the measured scope. Harness processes use CPU affinity 0,5; each
namespace-side child gets its exact 1–2 or 3–4 cpuset.

The only accepted pre-existing `perf.slice` runtime drop-ins are
`50-AllowedCPUs.conf` and, when present, `50-MemoryMax.conf` under
`/run/systemd/system.control/perf.slice.d/`. The current CPU file contains the
systemd-generated `AllowedCPUs=` list reset followed by the active saved mask
`AllowedCPUs=1-3`; the parser accepts that reset but rejects any other CPU
value or setting. The overlay saves the CPU file byte-for-byte, records both
file hashes, and restores the CPU file directly without reverting `perf.slice`,
so the memory cap stays in place. It checks the live cgroup masks and both
drop-in hashes before leaving the measured scope; a second locked pass checks
the saved cgroup masks and file hashes again. Any other pre-existing drop-in
remains a hard refusal.

The global workqueue mask at
`/sys/devices/virtual/workqueue/cpumask` and every existing per-workqueue
`cpumask` are saved, set to hexadecimal `21` (CPUs 0 and 5), and restored.
Every virtio network IRQ is moved to housekeeping CPUs after its original
affinity is saved. The R4b namespace path uses veth, which has no device IRQ;
the audit records per-CPU `/proc/interrupts` and `/proc/softirqs` deltas to
show where IRQ and network softirq work lands.

The in-scope exit handler restores the saved cgroup masks, IRQ affinities, and
workqueue masks, then verifies each live value. After reverting a temporary
systemd CPU property, systemd may leave the explicit full guest mask in
`cpuset.cpus` where the saved value was empty. The shared verifier accepts
that equivalent only when the live effective mask is still exactly `0-5`; it
rejects any narrowed or expanded real mask. Empty configured cgroup masks and
empty drop-in lists use an explicit manifest sentinel so tab-separated fields
cannot shift during verification. A second locked `perf-run`
reads the real cgroup files and verifies the same manifests after the first
scope has exited. `AllowedCPUs` and `EffectiveCPUs` systemd properties are
recorded for context; they are not the source of truth for CPU restoration.

## Matched kernel row and link offloads

The counted kernel comparison uses `kernel-plain`: the case creates `wgA` and
`wgB` with `ip link add ... type wireguard`, configures them with `wg set`, and
sets both tunnel MTUs to 1420. It has no NetBird process or setup path. The
older NetBird kernel row used `wt0` at MTU 1280 and remains a separately labeled
historical reference. Each NetBird row took 174–178 seconds in the last hold,
so the pair is not repeated in a cut hold.

Each row records `ethtool -k` for both tunnel interfaces and the `a0`/`b0` veth
underlay interfaces. `offloads/offloads.json` records each link's MTU and
whether the reported GSO and GRO feature groups have enabled features; the raw
`ethtool -k` and `ip -o link` outputs remain beside it. `version.json` records
the engine's configured userspace UDP GSO/GRO path where that metadata is
known. The `ethtool` flags describe interface configuration, not packet
counts, so reports do not claim that an enabled feature processed a specific
number of packets.

Each loaded-window audit samples the per-CPU steal field from `/proc/stat`.
The JSONL samples retain the tick values; each `summary.json` reports the
window delta by CPU, test-CPU seconds, housekeeping-CPU seconds, and the
percentage of test-CPU time lost to steal. This lets the owner compare the
two perf-VM placements without mixing steal from separate windows.

## Tokio worker locality trial

The locality rows use the exact same fork binary and source SHA as the J88i
fairness rows. Set `H2H_MATRIX_LOCALITY=1` on `perf-all.sh`; it crosses the
`perf-run` scope explicitly. In a hold, this pins only the GotaTun
`candidate-a` and `candidate-b` rows, leaving the two control rows at default
placement. After the first-packet warmup, the harness enumerates each
endpoint's live `/proc/<pid>/task` threads, selects only the known Tokio worker
`comm` values (`tokio-rt-worker` in the locked Tokio 1.50, or the older
15-byte-truncated `tokio-runtime-w`), sorts them by TID, and pins them
round-robin to that endpoint's two-CPU side mask. The assigned TID/CPU pairs
are saved beside the endpoint logs. If the process has no Tokio workers or
`sched_setaffinity` fails, the row fails before sampling. If a new Tokio worker
appears later with the wider side mask, the loaded-window audit rejects the
mismatch.

After pinning, the case exports both endpoint PIDs to the audit. The audit
permits a singleton thread mask only for one of those PIDs when the worker
name is `tokio-runtime-w`, placement is `round-robin`, and the row tag is a
hold candidate or an explicit `gotatun-j88i-locality-33ca6fe-N` row. The
summary records the PID allowlist.
Process comm is not used to identify the endpoints because the shipped test
binary uses a distinct comm name. All other threads retain the exact side
mask, and the ordinary non-kernel runnable-task, CPU-steal, IRQ, softirq, and
unrelated-kernel-worker checks still apply. This is a runtime placement
experiment; it changes no product source or D348 side mask.

Fairness and locality matrices are separate pinned, five-window runs. Each
window contains the shipped executable and matched kernel/wireguard-go
controls. Results are labeled `uncalibrated, owner-directed`; the final table
column reports the max/min spread across the five shipped-control rows for
each metric. A candidate gain counts only when it is larger than that spread.
The prior pinned calibration failure is reported as 1.03% at eight-flow
throughput and 5.7% at one-flow loss-aware p99; unpinned history stays
separate.

## Interference audit

The audit samples `/proc/<pid>/status`, `/proc/<pid>/schedstat`, and each
thread's `/proc/<pid>/task/<tid>/sched` record once per second while both sides
run. It records `State`, `Cpus_allowed`, the current CPU, cumulative runtime,
run-queue delay, and `se.nr_migrations`. `summary.json` reports the migration
counter delta for each scoped thread and the total for the loaded window. A
runnable non-kernel task whose allowed CPU list intersects CPUs 1–4 rejects
the window. Every process in the two test scopes must also have exactly its
side's expected `Cpus_allowed_list`.

Bound kernel workers are classified only when all of these match: the task is
a child of PID 2 (`kthreadd`), its cgroup is `/`, its name is `kworker/N:*` or
`ksoftirqd/N`, and its `Cpus_allowed_list` is exactly the single CPU N. The
audit sums each worker's `/proc/<pid>/schedstat` runtime delta by CPU and role,
and reports both those subtotals and the total over the loaded window.
`ksoftirqd/N` is classified as network softirq workload. In the kernel-NetBird
case, `kworker/N:*wg-crypt-wt0` is classified as WireGuard crypto workload.
These workers perform the measured network or crypto workload for their row:
their schedstat deltas are reported by worker, CPU, role, and total, but they do
not use the unrelated-background budget. The audit sums only matching workers
classified as `background` and rejects a window when that unrelated runtime
exceeds 0.5% of the four test CPUs' wall-clock time; exactly 0.5% is allowed.
Any non-kernel runnable task allowed on a test CPU remains a hard failure.
Other root kernel tasks are reported separately.
The `perf` utility and `/proc/sched_debug` are not available on this VM. The
per-thread migration counters, `schedstat` run-delay deltas, and sampled
runnable states are therefore the scheduler evidence for this setup; the
report records that limitation.
Validation's LAN throughput window is 10 seconds, matching counted windows, so
a short smoke interval does not let one brief bound-worker burst dominate the
0.5% unrelated-work budget. Other validation probes keep their smoke counts.

## Three-control calibration

Calibration runs the same fork binary three times as `control-a`, `control-b`,
and `control-c`, with 3,600 LAN probes per flow count. The script checks the
raw ping footer to confirm that each flow actually sent 3,600 probes. It
calculates p50 from received replies and loss-aware p99 by adding one infinite
sample for every missing reply before ranking the raw RTTs.

The loaded fixed-count ping uses `-c 3600` without iputils' overall `-w`
deadline. With `-w`, iputils waits for the requested number of replies and
can transmit additional probes after loss, so that flag would invalidate an
exact sent-probe count.

For each metric, the reported repeat spread is `(maximum / minimum - 1) × 100`;
the control is the metric-wise median of the three rows. The published
unpinned same-control history sets these pass limits:

| Metric | 1 flow | 8 flows |
|---|---:|---:|
| Throughput max/min spread | 1.6% | 0.8% |
| Loss-aware p99 max/min spread | 3.2% | 5.9% |

The overlay reports p50 and CPU-seconds/Gbit spreads too. No unpinned limits
for those metrics were published with the same-control history, so they are
reported but do not change the calibration pass. Pinned values are compared
only with pinned values; unpinned history remains a separate reference.

A failed audit, incomplete raw probe set, or spread above a published limit
fails calibration and normally keeps candidate holds disabled. A passing
calibration is the prerequisite for counterbalanced candidate holds.

The owner may explicitly direct a counted hold to proceed after a failed
calibration. Such a hold keeps its own result and evidence, but the calibration
remains failed; every report must state the failed spread and label the hold
owner-directed. Do not combine those pinned results with unpinned history or
describe the calibration as passing.
